0 · Orientation

Post-Merge Ethereum runs as two cooperating processes: a Consensus Layer (CL/beacon) node that owns fork choice, attestations and finality, and an Execution Layer (EL) node that owns the EVM, state trie and the transaction pool. They are wired together by a single, narrow JSON-RPC surface — the Engine API on port 8551, JWT-authenticated — and a tight choreography of three families of calls: engine_newPayload, engine_forkchoiceUpdated, and engine_getPayload. Every method version, every status code and every timeout in this surface is load-bearing for liveness and safety.

This site documents the canonical dance and every meaningful client deviation across the five major ELs (GethNethermindErigonBesuNimbus-eth1) and the five major CLs (PrysmLighthouseTekuLodestarNimbus-eth2) as of April 2026 — i.e. post-Pectra (May 2025) and post-Fusaka/Osaka (Dec 3 2025), with PeerDAS active.

Three-call dance

newPayload = "validate this block." forkchoiceUpdated = "this is the head; optionally start building." getPayload = "give me the block you've been building."

Who owns what

CL owns: head selection, attestations, finality, blob/column DAS, validator duties. EL owns: EVM execution, state, txpool, blob/cell mempool, request collection (deposits/withdrawals/consolidations).

Single authoritative driver

Exactly one CL drives FCU. Many CLs may share a JWT secret and call newPayload, but multi-driver fork choice is undefined.

1 · Engine API foundations

The Engine API is specified in ethereum/execution-apis under src/engine/{paris,shanghai,cancun,prague,osaka,common,authentication,identification}.md. It is a JSON-RPC 2.0 dialect with strict, fork-versioned methods, a constrained PayloadStatusV1 state machine, and bounded timeouts. The CL is the only client of this API; the EL must serve it on a port distinct from the public eth_* JSON-RPC.

1.2 JWT, transport, port

  • Algorithm: HS256 only; alg:none must be rejected. 32-byte (256-bit) secret in hex.
  • Required claim: iat within ±60 s of EL clock. Optional: id, clv. Unknown claims must be ignored.
  • Default port: 8551, distinct from public eth_* JSON-RPC. HTTP: per-request Authorization: Bearer <jwt>. WebSocket: upgrade handshake authenticated only; frames are not. IPC: no JWT (filesystem permissions).
  • Required eth namespace methods on the engine port: eth_blockNumber, eth_call, eth_chainId, eth_getCode, eth_getBlockByHash, eth_getBlockByNumber, eth_getLogs, eth_sendRawTransaction, eth_syncing.

1.3 PayloadStatus state machine

stateDiagram-v2 [*] --> SYNCING: parent unknown [*] --> ACCEPTED: side-chain, well-formed [*] --> VALID: full validation OK [*] --> INVALID: state transition fails [*] --> INVALID_BLOCK_HASH: blockHash != keccak(RLP(header)) SYNCING --> VALID: data fetched, replayed OK SYNCING --> INVALID: replay fails ACCEPTED --> VALID: branch becomes canonical ACCEPTED --> INVALID: branch invalidated VALID --> [*] INVALID --> [*]: idempotent cannot become VALID INVALID_BLOCK_HASH --> [*] note right of INVALID latestValidHash: 32-byte ancestor hash, or 0x00..00 terminal-PoW failure, or null cannot determine end note note right of VALID latestValidHash = payload.blockHash end note

engine_forkchoiceUpdated response is restricted to {VALID, INVALID, SYNCING} — never ACCEPTED nor INVALID_BLOCK_HASH. Idempotency invariant: a payload that returned VALID may never later become INVALID, and vice versa, regardless of subsequent EL state.

2 · Startup choreography

sequenceDiagram autonumber participant Op as Operator participant CL participant EL Op->>EL: start authrpc on 8551 with jwt.hex Op->>CL: start with execution endpoint and jwt.hex CL->>EL: HTTP POST with Authorization Bearer JWT EL-->>CL: 200 OK, or 401 on skew/HMAC mismatch CL->>EL: engine_exchangeCapabilities(newPayloadV4, FCUV3, getPayloadV5, getBlobsV3) EL-->>CL: list of methods EL supports CL->>EL: engine_getClientVersionV1(CL version) EL-->>CL: EL version CL->>EL: engine_forkchoiceUpdatedV3(head, safe, finalized, null) alt EL has the head EL-->>CL: VALID with payloadId null else EL does not have the head EL-->>CL: SYNCING with payloadId null CL->>CL: enter optimistic mode and suspend validator duties end

Post-Merge there is no TTD handshake any more — engine_exchangeTransitionConfigurationV1 is deprecated since Cancun. The CL bootstraps either from genesis or from a weak-subjectivity checkpoint state; in both cases it derives the EL block hash of the anchor's latest_execution_payload_header and feeds it as finalizedBlockHash in the very first FCU. The EL responds SYNCING until it has actually downloaded that block and its state.

3 · Sync modes

For all ELs, beacon-driven sync is idempotent in the FCU: re-issuing FCU with the same head simply re-confirms the target. Geth's delayPayloadImport rejects newPayload while in snap sync — "snap sync relies on direct database injections and cannot afford concurrent out-of-band modifications via imports."

4 · Optimistic sync (CL side)

Defined in consensus-specs/sync/optimistic.md. The CL imports beacon blocks without verifying their execution payload, accepting EL responses of SYNCING or ACCEPTED as NOT_VALIDATED. The block enters fork choice with full LMD weight, but the validator client refuses to attest, propose, or sync-vote.

stateDiagram-v2 [*] --> NOT_VALIDATED: EL returns SYNCING or ACCEPTED, parent ok NOT_VALIDATED --> VALIDATED: EL later returns VALID for this or descendant NOT_VALIDATED --> INVALIDATED: EL returns INVALID for this or descendant VALIDATED --> [*] INVALIDATED --> [*] note right of NOT_VALIDATED Block in fork choice with weight Validator duties forbidden Beacon API execution_optimistic equals true end note note right of INVALIDATED Cascade rules: lvh ancestor hash invalidates child and descendants lvh 0x00..00 invalidates from merge block down lvh null invalidates just this block lvh unknown is treated as null end note

SAFE_SLOTS_TO_IMPORT_OPTIMISTICALLY = 128 (configurable). A block is an optimistic candidate iff its parent already has an execution payload or it is at least 128 slots in the past — protecting only the merge transition block from fork-choice poisoning.

Implementation map. Prysm: ForkChoiceStore.SetOptimisticToInvalid(headRoot, parentRoot, payloadParentHash, lvh) in beacon-chain/blockchain/execution_engine.go. Lighthouse: ProtoArrayForkChoice::process_invalid_execution_payload + ExecutionStatus::{Optimistic,Valid,Invalid}. Teku: ForkChoiceStrategy.applyDeltas with proto-array port. Lodestar: ExecutionPayloadStatus enum in packages/beacon-node/src/execution/engine/interface.ts. Nimbus-eth2: optimistic state in blockchain_dag + el_manager.nim; supports multi-EL violation detection.

FCU frequency: typically 2–4 calls per slot (head update; head flip after attestations; proposer-prep; possibly an override after should_override_forkchoice_update). Anti-pattern: attaching payloadAttributes to every FCU regardless of whether the node will propose — wastes EL build cycles and pollutes the txpool snapshot.

MEV-Boost

The Engine API has no awareness of builders. mev-boost is a sidecar between CL and relay; the CL signs a blinded block over a SignedBuilderBid header, then either un-blinds it via the relay or — if the relay times out — falls back to the local engine_getPayload. Once the validator has signed either a beacon block or a blinded block for that slot, signing the other is slashable; this is why CLs must always start the local build in parallel.

7 · Reorgs & finality

A reorg manifests at the engine layer purely as an FCU whose headBlockHash is not a descendant of the previously-communicated head. The EL must rewind state to the most recent common ancestor, replay the new branch, return orphaned txs to its mempool, and re-emit log subscriptions with removed:true/false.

flowchart LR A["A_3"] --> A4["A_4"] --> A5["A_5 - was head"] A4 --> B5["B_5 - new head"] B5 --> B6["B_6"] classDef orphan fill:#2a1414,stroke:#5a2222,color:#fda4a4 classDef live fill:#0e2316,stroke:#1d5530,color:#86efac class A5 orphan class A,A4,B5,B6 live

Single-slot reorgs are driven by proposer boost and the get_proposer_head rule (eight conjoined predicates including head_late, head_weak < 20% committee weight, parent_strong ≥ 160% committee weight, finalization_ok ≤ 2 epochs since finality). Lighthouse pioneered this in production; --disable-proposer-reorgs opts out.

Deep reorgs are bounded by FFG finality. The EL is permitted to drop sidechain state and prune below finalizedBlockHash; it must never prune above it. safeBlockHash is the EL hash of the current justified checkpoint — it has no special pruning effect, but is exposed as "safe" on eth_getBlockByNumber.

8 · Cancun/Deneb (mainnet 13 March 2024)

  • engine_newPayloadV3(payload, expectedBlobVersionedHashes, parentBeaconBlockRoot). The EL must verify, even during sync, that the concatenated blob_versioned_hashes across all type-3 transactions in arrival order equals expectedBlobVersionedHashes; mismatch ⇒ {INVALID, lvh=null}.
  • BlobsBundleV1 = {commitments[], proofs[], blobs[]} (one KZG proof per blob). EL must verify verify_blob_kzg_proof_batch before returning getPayloadV3.
  • parentBeaconBlockRoot oracle: contract 0x000F3df6D732807Ef1319fB7B8bB8522d0Beac02, system caller 0xfff..fffe, HISTORY_BUFFER_LENGTH=8191, dual ring buffers (timestamps + roots).
  • KZG split: EL verifies blob proofs at mempool ingress and at getPayload; CL verifies blob sidecars match commitments via SSZ inclusion proof.
  • engine_getBlobsV1: opportunistic mempool fetch by versioned hash. Empirical hit rate 70–80 % on mainnet.

9 · Prague/Electra — Pectra (mainnet 7 May 2025)

  • engine_newPayloadV4(payload, vh[], pbbr, executionRequests) — adds the EIP-7685 requests bus. Each element is request_type || request_data, ascending by type; empty request_data excluded; duplicates / out-of-order / null ⇒ -32602. The EL recomputes requests_hash = sha256(sha256(req_i)..) and folds it into blockHash validation.
  • Three request types: 0x00 deposits (EIP-6110), 0x01 withdrawal requests (EIP-7002), 0x02 consolidations (EIP-7251). Collected by EL via predeploy storage / contract events; not in receipts; flow EL→CL.
  • EIP-7691 raises blob target/max from 3/6 to 6/9. EIP-7702 adds SET_CODE_TX_TYPE 0x04 for EOA delegation. EIP-7549 (CL-only attestation reformat) is transparent to engine API.
  • engine_forkchoiceUpdatedV3 is reused for Prague (no new attribute fields); BlobsBundleV1 retained — Pectra did not move to cell proofs.

10 · Fusaka/Osaka — PeerDAS (mainnet 3 December 2025)

  • engine_getPayloadV5 returns BlobsBundleV2: len(proofs) = CELLS_PER_EXT_BLOB × len(blobs) = 128 × N, i.e. one proof per cell after 1D Reed–Solomon extension (128 cells per extended blob, 64 original + 64 extension).
  • engine_getBlobsV2 is all-or-nothing (returns null literal if any hash unknown); engine_getBlobsV3 permits per-position null for partial responses (preferred for column reconciliation, PR #671). Pre-Osaka engine_getBlobsV1 returns -38005.
  • No engine_newPayloadV5 in the canonical Osaka spec — payload structure is unchanged; only the bundle and blob-fetch shapes change. Some implementations (Reth doc strings) reference V5 as a forward-looking placeholder for post-Amsterdam; not yet canonical.
  • Cell-proof verification: senders pre-compute all 128 cell proofs per blob (off the proposer's critical path). EL mempool batch-verifies on ingress. CL custodies a subset of the 128 columns (4 for full nodes, 128 for supernodes), runs DAS over SAMPLES_PER_SLOT random columns, and reconstructs missing columns when ≥ 50 % are held.
  • Blob Parameter-Only forks (EIP-7892) raise target/max without a full upgrade. BPO1 → 10/15 (Dec 2025); BPO2 → 14/21 (Jan 2026). EIP-7918 floors blob basefee against execution gas cost. EIP-7825 caps per-tx gas at 16,777,216. EIP-7934 caps RLP block size at 10 MiB. EIP-7935 raises default gas limit to ~60 M.

11 · EIP-4444 history expiry & era files

Phase 1 live as of 8 July 2025. All major ELs may drop pre-Merge bodies and receipts (300–500 GB savings). Pre-Merge headers must still be served on devp2p. Phase 2 (rolling 1-year window) is not yet shipped on mainnet as of April 2026; EIP-7801 standardizes range advertising.

Pre-Merge data is recovered out-of-band from Era1 files (e2store TLV, ≤ 8192 blocks per file, snappy framing, accumulator hash), Era files (post-Merge beacon archive embedding EL payloads), or the Portal Network (Trin, Fluffy, Geth's blsync). Per-client status: Geth/Reth/Erigon/Nethermind/Besu (--era1-import-prepipeline-enabled) all support import; Erigon distributes via BitTorrent natively; Nimbus-eth1 uses Era1+Era as a primary sync mode.

EL · Geth (go-ethereum)

  • Engine package: eth/catalyst/ — ConsensusAPI struct in api.go (~1230 LoC). Methods: NewPayloadV1..V5, ForkchoiceUpdatedV1..V4, GetPayloadV1..V6, GetBlobsV1..V3, plus stateless witness variants (NewPayloadWithWitnessV1..V4, ExecuteStatelessPayloadV1..V4).
  • Locks: forkchoiceLock + newPayloadLock serialize concurrent calls (CL retry race during DB compaction).
  • Sync: eth/downloader.BeaconSync(mode, head, final) + BeaconExtend; delayPayloadImport rejects newPayload while in snap mode. SetBadBlockCallback(api.setInvalidAncestor) wires bad-block discovery.
  • Block production: miner.BuildPayload + payload.update() goroutine, Recommit=2s. No native MEV-Boost; Flashbots builder fork adds it externally.
  • Blobpool: core/txpool/blobpool/ backed by holiman/billy file shelves (<datadir>/geth/blobpool/); 2.5 GB datacap, persisted across restarts. BlobPool.reinject handles V0→V1 migration at Osaka (~140 ms/blob on M1 Pro per code comment).
  • State: PBSS default since 1.14 (--state.scheme=path); inline pruning bounded by StateHistory (~90 000 blocks). HBSS→PBSS migration historically produced "missing trie node" errors.
  • Quirks: blobpool corruption #28990 (1.13.11/12); ResolveFull blocks on cond.Wait #28242; eth/68 removed in 1.17.x (only eth/69+).
  • blsync: cmd/blsync + beacon/light/ drives any EL via Engine API using a beacon light client.

EL · Nethermind

  • Engine plugin: src/Nethermind/Nethermind.Merge.Plugin/ — EngineRpcModule : IEngineRpcModule dispatches to per-method handlers (ForkchoiceUpdatedHandler, NewPayloadHandler, GetPayloadV1..V5Handler, GetBlobsHandler). 14-arg DI in handler constructors (incl. IInvalidChainTracker, IMergeSyncController, IBeaconPivot).
  • Routing: JsonRpcProcessor registers engine namespace on a separate host/port (JsonRpc.EngineHost, default 127.0.0.1:8551). ResultWrapper<T> is the universal return type.
  • Sync: MultiSyncModeSelector picks among FullSync, SnapSync, FastSync, BeaconHeaders, etc. Snap default since v1.14 (late 2022). Beacon-driven via BeaconPivot + MergeSyncController + BeaconHeadersSyncFeed.
  • Engine GC tuning: Merge.PrioritizeBlockLatency=true suppresses GC during Engine calls; Merge.SweepMemory=Gen1; Merge.MemoryCompaction=Yes.
  • Block production: PayloadPreparationService + BlockImprovementContext. Improvements weren't always cancelled on getPayload — issue #8459.
  • Blobs: BlobTxStorage in RocksDB; BlobTxDistinctSortedPool in mempool.
  • Quirks: 21 Jan 2024 consensus bug (revert-message overflow PR #6226); v1.25.2 hotfix. v1.35.1 withdrawn for "block production and sync issues." FastSyncEnabled = FastSync || SnapSync caused user confusion (#4131). DB corruption hard-fail changed to Environment.Exit in 1.35.x. Nethermind co-authored 7 of the 12 Fusaka EIPs.

EL · Erigon (and Caplin)

  • Staged sync: 17 stages in eth/stagedsync/ — Snapshots, Headers, CumulativeIndex, BlockHashes, Bodies, Senders, Execution, HashState, IntermediateHashes, Account/StorageHistoryIndex, LogIndex, CallTraces, TxLookup, Finish. Each has ExecFunc+UnwindFunc. ETL framework buffers writes, heap-merges to MDBX.
  • Engine API: turbo/engineapi/EngineServer. newPayload at tip runs single-block Execution+InterHashes, not a full pipeline. The block-by-block Engine API is acknowledged as an impedance mismatch with batched staged execution (issue #7173).
  • Caplin: in-process CL under cl/ — default in Erigon 3 (--externalcl=false). Communicates with execution in-process via execution_client.ExecutionEngine interface; --caplin.use-engine-api falls back to standard Engine API for testing/degraded networks. Discv5 on UDP 4000 / TCP 4001. Erigon 3 markets itself as "the world's first all-in-one EVM node" with validator/proposer support.
  • State: MDBX (libmdbx) with plain state (raw 20-byte address keys; HashedState derived only for compatibility). Erigon 3 introduces domain/history/idx/accessor file layout, transaction-granular history, no receipts stored by default (re-executed on demand). E3.3 added historical proofs via Elias-Fano (--prune.include-commitment-history).
  • Process model: txpool, sentry (P2P), downloader, rpcdaemon can run as separate binaries over private gRPC (9090 default; reserved 9092/9093/9094).
  • Block production: mining stages (stage_mining_create_block/exec/finish); fixed in #3575 ("Hanging ForkChoice").
  • Quirks: issue #9786 context canceled on heavy RPC load. HDD mode "stays a few blocks behind tip." E3.1 deprecated E2 in May 2025.

EL · Besu

  • Engine methods: org.hyperledger.besu.ethereum.api.jsonrpc.internal.methods.engine.* — EngineNewPayloadV1..V4, EngineForkchoiceUpdatedV1..V3, EngineGetPayloadV1..V4, EngineGetBlobsV1/V2, EngineExchangeCapabilities. Wired in ExecutionEngineJsonRpcMethods (V4 filtered out pre-Prague).
  • Stack: Vert.x + Netty; default Engine port 8551, host allowlist defaults to localhost,127.0.0.1; --engine-jwt-secret required (no auto-gen).
  • Plugin SDK: BesuPlugin via ServiceLoader; BesuContext, RpcEndpointService, BlockchainService, TransactionPoolService. Most builder/MEV integrations hook here.
  • Controller: BesuControllerBuilder assembles ProtocolSchedule, EthProtocolManager, DefaultSynchronizer, MergeCoordinator, WorldStateArchive. Subclasses for IBFT/QBFT/Clique merged with MergeBesuControllerBuilder.
  • Sync: SNAP default since 24.3 (PR #4462 moved pivot to CL safe block); FAST deprecated 24.12. BackwardSyncContext handles backfill (issue #5411 documents 2023 thrash with Nimbus on Sepolia).
  • Bonsai vs Forest: Bonsai (default since 24.3) keeps flat key-value state with per-block TrieLog; ~650 GB full-node footprint, O(1) account lookups. --bonsai-historical-block-limit default 512. --bonsai-limit-trie-logs-enabled default-on since 24.6. Bonsai cut block-import median from 1.71 s → 0.49 s on m6a.xlarge. Forest required for archive (~12 TB).
  • Block production: MergeBlockCreator + BlockTransactionSelector; --block-txs-selection-max-time ~1800 ms.
  • Quirks: JVM heap tuning needed (~8 GB recommended). #6896 OOM with Blockscout. Native crypto post-Pectra broke Windows mainnet (#8418). 25.x parallel state-root computation (#9576) and parallel tx processing.

EL · Nimbus-eth1

  • Status: mainnet-eligible but minority. Directory renamed nimbus/ → execution_chain/; binary nimbus_execution_client. PR #3646 introduced a single nimbus binary bundling EL+CL in two threads sharing a datadir (the team self-criticizes the "JSON between threads" wiring).
  • Engine API: execution_chain/rpc/engine_api.nim. Implements V1..V4 + getBlobsV1/V2 + capabilities. Built on nim-json-rpc + nim-web3.
  • Sync: Era1 (pre-Merge) + Era (post-Merge) ingest is the primary mainnet bootstrap (~few days); devp2p eth/68+ for tip; nrpc sync binary replays via Beacon API; pre-synced DB tarball from eth1-db.nimbus.team. No native snap sync as of April 2026.
  • State: Aristo flat-state on RocksDB (replaced earlier hexary impl).
  • Portal: portal/ directory (formerly fluffy/) — separate nimbus_portal_client binary; long-stated plan to integrate Portal into the EL is partial.
  • Verified Proxy: nimbus_verified_proxy/ — light-client + eth_getProof wrapper turning untrusted RPC providers into trustless sources.
  • Why interesting: Nim compiles to C, small binaries, low GC pressure, runs on Pi/Android (Termux).

CL · Prysm

  • Repo: moved to github.com/OffchainLabs/prysm; module path github.com/OffchainLabs/prysm/v7/....
  • Engine client: beacon-chain/execution/{service.go,engine_client.go,rpc_client.go} — execution.Service wraps go-ethereum's rpc.Client with a jwtTransport. Sentinel errors: ErrAcceptedSyncingPayloadStatus, ErrInvalidPayloadStatus.
  • Block processing: beacon-chain/blockchain/execution_engine.go — Service.notifyForkchoiceUpdate and Service.notifyNewPayload. INVALID handling: calls ForkChoiceStore.SetOptimisticToInvalid(headRoot, parentRoot, payload.ParentHash, lvh), removeInvalidBlockAndState, recurses to ForkChoiceStore.FullHead, re-issues FCU.

  • Builder/MEV-Boost: beacon-chain/builder/Service with circuit-breaker (--max-builder-epoch-missed-slots, default lowered to 5 in v4.0). v7.x raised default builder gas limit 45M→60M.
  • Incidents: Apr 2021 deposit-tree bug; 11–12 May 2023 old-target attestation state-replay (fixed v4.0.4); 4 Dec 2025 Fusaka near-miss in v7.0.0 — same conceptual class (~382 ETH attestation rewards lost; --disable-last-epoch-targets).

CL · Lighthouse

  • Engine client: beacon_node/execution_layer/. ExecutionLayer<E:EthSpec> wraps Inner; Engine struct holds HttpJsonRpc, payload_id_cache: LruCache, state: RwLock<State> (Synced/Online/Offline/AuthFailed), latest_forkchoice_state. EngineApi trait in engine_api.rs; auth via jsonwebtoken in auth.rs.
  • Block processing: BeaconChain<T>::process_block returns Result<AvailabilityProcessingStatus, BlockError>; PayloadVerificationStatus::{Valid,Optimistic,Verified}; execution_payload.rs contains notify_new_payload, process_payload_status.
  • Fork choice: originator of proto_array (cache-friendly array-backed DAG) — consensus/proto_array/; ExecutionStatus::{Optimistic,Valid,Invalid} recorded per node.
  • Sync: SyncManager in beacon_node/network/src/sync/; RangeSync, BlockLookups, BackFillSync. Backfill rate-limited since v4.1 (~20 slots/s).
  • Validator/builder: ExecutionLayer::get_full_payload_caching races local vs builder; --always-prefer-builder-payload since v3.5.
  • DB/state: LevelDB; hierarchical state diffs (cold_hdiff_buffer_cache_size, hot_hdiff_buffer_cache_size).
  • Client-share concern: ~52–56 % of CL nodes (Dec 2025 MigaLabs). Pioneered proposer boost (40 % weight, default since v2.5). "Fullhouse" experiment embeds Reth as a library (RethEngineApi calling ConsensusEngineHandle directly).

CL · Teku

  • Engine client: ethereum/executionclient/. Channel stack: ExecutionLayerChannel (renamed from ExecutionEngineChannel) ← ExecutionLayerManagerImpl ← ExecutionEngineClient ← Web3JExecutionEngineClient (Web3j + OkHttp). All async over Teku's SafeFuture<T>.
  • Block processing: BlockImporter → BlockManager → ForkChoice.onBlock → StateTransition.initiate. MergeTransitionBlockValidator validates terminal block conditions.
  • Sync: ForwardSync + BackwardSync + SyncStateTracker (STARTING/SYNCING/IN_SYNC/OPTIMISTIC). Checkpoint sync via --checkpoint-sync-url or --initial-state; only block root stored at checkpoint (Lighthouse stores both block and state).
  • Builder API: --builder-endpoint, --builder-bid-compare-factor (default 90 %); registrations sent in batches of 100.
  • JVM: Java 21 today, Java 25 incoming; ~4–8 GB heap recommended; SafeFuture + AsyncRunner framework. Web3Signer external signer is the production validator setup (slashing-protection DB, HSM/Vault).
  • Incidents: 11–12 May 2023 old-target attestations (with Prysm); Aug 2022 Besu pairing timeouts (engine_exchangeTransitionConfiguration); Mar 2026 mainnet beacon-state serialization regression (mandatory release); Dec 2025 default DB LevelDB→RocksDB migration requiring re-checkpoint-sync.

CL · Lodestar

  • Maintainer: ChainSafe; Apache-2.0 monorepo at github.com/ChainSafe/lodestar. Increasing Zig adoption for performance-critical paths (repo description: "Zig and TypeScript ecosystem"). Strong light-client lineage (@lodestar/light-client runs in browsers).
  • Engine client: packages/beacon-node/src/execution/engine/. ExecutionPayloadStatus enum mirrors EL responses. CLI: --execution.urls, --jwt-secret, --jwtId.
  • Validator client: separate process via Beacon REST API (not in-process by default).
  • Sync: SyncManager + RangeSync + UnknownBlockSync + Backfill — same pattern as Lighthouse; checkpoint sync via --checkpointSyncUrl.
  • V8 constraint: single-threaded event loop is the performance ceiling; selective worker_threads for keystore decryption (5× speedup). Default 8 GB heap; holesky-rescue branch raised to 32 GB.
  • Holesky 2025: followed Geth onto bad chain; constant OOM until patches; checkpoint-states ballooned to ~250 MB each (~56 GB/day) until DEFAULT_MAX_CP_STATE_ON_DISK patch (PR #7510). Postmortem at blog.chainsafe.io.
  • Pairing quirk: Lodestar+Nethermind handshake bug on Holesky (NethermindEth/nethermind#7117) — only reproducible with Lodestar; since fixed.

CL · Nimbus-eth2

  • Engine client: beacon_chain/el/el_manager.nim. Multi-EL is unique: multiple --el URLs simultaneously; "Nimbus will act as an execution layer consensus violation detector, preventing the publishing of blocks that may trigger a catastrophic partitioning in the network." Per-URL JWT via #jwt-secret-file= URL fragments. Metrics: engine_api_responses, engine_api_request_duration_seconds, engine_api_timeouts.
  • Eth1: beacon_chain/eth1/eth1_monitor.nim (legacy deposit follower).

  • Incidents: v24.2.2 EIP-7044 incomplete (Holesky/Deneb near-miss); v26.2.0/.1 Merkle-tree cache invalidation in nim-ssz-serialization caused mainnet false-rejection of a valid block — operators on v26.1.0 or earlier "should verify they're still on the canonical chain, restart Nimbus otherwise."

Appendix · Spec uncertainties (April 2026)

  • No fusaka.md in execution-apis — the post-Prague file is osaka.md. "Fusaka" is the combined Fulu (CL) + Osaka (EL) hardfork name in operator parlance.
  • No engine_newPayloadV5 in canonical Osaka spec; Reth doc strings reference an "amsterdam.md" placeholder.
  • EIP-4444 Phase 2 (rolling 1-year window) not yet shipped on mainnet despite some 2025 press conflating it with Phase 1.
  • BPO1/BPO2 activation slots have minor discrepancies across sources (Foundation announcement vs secondary outlets — Dec 9 vs Dec 17 for BPO1).
  • ACCEPTED vs SYNCING divergence: some ELs never return ACCEPTED. INVALID_BLOCK_HASH phasing out per #270 — modern clients fold into {INVALID, lvh=null}.
  • JWT hot reload not specified — all major clients require restart.
  • Nimbus-eth1 default Engine port: 8551 in user-facing docs, 8550 in some Status-internal Ansible roles. Verify per release.
  • Erigon Caplin "Phase" maturity: the team blog claims Phase 2 (in-process Erigon API) shipped, but the existence of --caplin.use-engine-api shows Engine-API remains a supported in-process path.
  • April 2024 Nethermind incident referenced in some narratives appears to conflate with the 21 January 2024 consensus bug (revert-message overflow); a distinct April 2024 mainnet incident is not corroborated by primary sources.
  • "April 2023 Capella issue": the actual Prysm/Teku finality delay was 11–12 May 2023, post-Capella, not at Capella activation.
